# Week 01：目标岗位需求与项目能力映射

## 1. 文档目标

本文档用于从秋招求职岗位的角度，反向确定“企业可信文档分析 Agent”后续必须实现、必须评测和必须保留证据的能力。

前序文档已经回答了以下问题：

- `01_mvp_report_inventory.md`：项目使用哪些文档，数据质量是否满足 MVP；
- `02_evaluation_design.md`：系统需要回答哪些问题，以及如何判定成功或失败；
- `02a_mvp_question_catalog.md`：74 道 MVP 问题如何覆盖不同任务；
- `03_platform_boundary.md`：哪些能力属于通用平台，哪些属于金融领域适配层，以及当前 MVP 不做什么。

本文档进一步回答：

1. 四类目标岗位分别希望从该项目中看到什么；
2. 哪些模块是项目成为“简历主项目”的必要条件；
3. 哪些能力需要通过真实代码、实验、日志和文档证明；
4. 哪些能力属于后续增强项，不应阻塞 MVP；
5. 简历和面试中应根据岗位选择不同的表达重点；
6. 该项目能够证明什么，以及不能过度声称什么。

本文档不负责设计具体代码目录、类结构、数据库表和运行时工作流。上述内容将在 `05_initial_architecture.md` 和后续周次中继续落实。

---

## 2. 本文档在项目中的位置

Week 1 的任务顺序为：

```text
业务与数据范围
    ↓
评测问题与成功标准
    ↓
平台层与金融领域边界
    ↓
目标岗位需求与能力映射
    ↓
初始系统架构
```

因此，本文档位于“业务定义”与“架构设计”之间。

它的核心作用不是继续增加功能，而是建立一套求职导向的优先级判断标准：

```text
岗位需要什么
    ↓
项目必须证明什么
    ↓
需要实现哪些模块
    ↓
需要设计哪些评测
    ↓
需要保留哪些可验证产物
```

后续选择技术方案时，不以“技术是否新”作为主要判断依据，而应优先判断：

- 是否解决当前业务问题；
- 是否能通过固定评测集验证；
- 是否能够形成可复现结果；
- 是否能在简历中形成可靠表述；
- 是否能够在面试中解释设计原因、替代方案和失败处理；
- 是否符合当前项目阶段，避免过早实现非核心功能。

## 3. 四类岗位共同关注的能力

虽然四类岗位的侧重点不同，但都会关注以下共同问题。

### 3.1 是否真正解决了业务问题

项目不能只展示“调用了 LangChain、LangGraph 或向量数据库”，而需要说明：

- 用户是谁；
- 用户需要完成什么审阅任务；
- 为什么普通 PDF 问答不够；
- 哪些问题需要结构化工具；
- 哪些问题需要文档检索；
- 哪些结论需要人工复核；
- 系统如何降低口径错误、数值错误和无证据回答。

### 3.2 是否完成了端到端闭环

最低闭环应覆盖：

```text
文档接入
→ 数据解析与元数据
→ 结构化事实或检索索引
→ 问题解析与任务路由
→ 工具调用或文档检索
→ 证据与数值校验
→ 引用生成
→ 最终回答、澄清或拒答
→ 日志、评测与失败分析
→ FastAPI 与 Docker 交付
```

只实现其中一个局部模块，不能独立构成完整的简历主项目。

### 3.3 是否有客观评测

项目结果不能只用几个演示问题证明。

至少需要保留：

- 固定评测集；
- 基线方案；
- 分层指标；
- 逐题结果；
- 失败类型；
- 配置和模型版本；
- 改进前后对比；
- 真实负面结果与局限性。

### 3.4 是否可追溯和可复现

面试官应能够从项目产物中确认：

- 数值来自哪张报表、哪个年度、什么口径和单位；
- 原因或风险来自哪个章节和页码；
- Agent 调用了什么工具和参数；
- 结论是否经过 Verifier；
- 高风险问题为何进入人工复核；
- 结果如何通过脚本重复运行。

### 3.5 是否理解技术取舍

每个重要模块都需要能够回答：

1. 为什么使用该方案；
2. 不使用它会出现什么问题；
3. 替代方案是什么；
4. 如何用实验验证；
5. 额外增加了多少延迟、成本或工程复杂度；
6. 失败时如何降级、重试、澄清或终止。

## 4. 目标岗位一：Agent / RAG 应用工程师

### 4.1 核心职责

该岗位更关注如何把大模型、检索、工具和后端服务组合成稳定可用的应用系统，典型职责包括：

- 企业文档解析、清洗、切分和索引；
- 基础 RAG、混合检索和 Reranker；
- Query Rewrite、Metadata Filter 和 Context Builder；
- Tool Calling 与确定性工作流；
- LangGraph 状态管理、分支、重试和终止；
- FastAPI、数据库、缓存、日志和 Docker；
- 检索评测、回答评测和端到端回归测试；
- 系统错误定位、性能分析和可观测性。

### 4.2 希望从本项目中看到的能力

| 岗位关注点 | 本项目应证明的能力 |
| --- | --- |
| 文档处理 | 12 份年报可稳定解析，并保留页码、章节、公司和年度元数据 |
| RAG | 能比较不同 Chunk、检索和重排方案，而不是只调用默认 Retriever |
| 上下文工程 | 能去重、过滤、压缩和按任务组织证据，控制上下文污染 |
| 工作流 | 不同任务能够进入结构化查询、计算、RAG、澄清或拒答分支 |
| 工具调用 | 参数经过 Schema 校验，工具错误能够重试、降级或终止 |
| 服务化 | 通过 FastAPI 提供稳定接口，并通过 Docker 启动 |
| 测试 | 单元测试、集成测试和固定评测集能够重复运行 |
| 可观测性 | 能查看 Trace、节点耗时、工具参数、检索结果和错误类型 |

### 4.3 最关注的项目成果

该岗位最看重以下成果：

1. 可运行的端到端企业文档 Agent；
2. 向量检索、BM25、Hybrid、Hybrid + Reranker 的统一对比；
3. Chunk 策略、Top-k、Metadata Filter 和 Context Builder 的实验记录；
4. LangGraph 工作流图和关键状态字段；
5. `/chat`、文档索引、任务状态和健康检查等 API；
6. pytest、API 集成测试、Dockerfile 或 Docker Compose；
7. 典型失败案例，包括检索失败、参数错误、上下文污染和工具异常；
8. 可以回放的一次完整请求轨迹。

### 4.4 对应项目模块

```text
Document Loader
Metadata Manager
Chunking
Retriever
Reranker
Context Manager
Planner
Tool Registry
LangGraph Runtime
Observability
Evaluation
FastAPI
Docker
```

### 4.5 简历表达重点

简历应优先突出：

- 端到端系统链路；
- 文档解析和检索优化；
- 工作流与工具调用；
- API、测试和部署；
- 客观评测与错误分析；
- 真实的效果、延迟和成本数据。

不应只写：

```text
使用 LangChain、LangGraph 和向量数据库搭建 RAG 系统
```

更合适的最终表达结构应为：

```text
业务问题 + 核心系统设计 + 关键技术改进 + 实测指标 + 工程交付
```

所有指标只能在后续真实实验完成后填写。

### 4.6 面试可能追问

- 为什么不能只用向量检索？
- BM25、Dense Retrieval 和 Hybrid Search 分别解决什么问题？
- RRF 为什么可以融合不同检索分数？
- Reranker 放在哪一层，为什么不直接对全部文档重排？
- Chunk Size 和 Overlap 如何影响 Recall、上下文长度和延迟？
- Metadata Filter 出错会造成什么后果？
- 如何区分检索失败与生成失败？
- 为什么使用 LangGraph，而不是一个自由循环 Agent？
- 如何避免 Agent 无限循环和重复调用工具？
- FastAPI 接口为什么需要异步、任务状态和结构化错误码？
- 如何实现请求追踪、失败复现和回归测试？
- Docker 中包含哪些服务，数据库和缓存分别承担什么职责？

### 4.7 该项目之外仍需补强

- Python 工程基础；
- SQL 与基础数据库设计；
- Redis、缓存和幂等概念；
- HTTP、并发和常见后端问题；
- 操作系统、网络、数据库等计算机基础；
- ACM 模式算法题。

## 5. 目标岗位二：Agent 算法工程师

### 5.1 核心职责

该岗位更关注 Agent 决策过程本身的正确性、稳定性和可优化性，典型职责包括：

- 意图识别与任务路由；
- Query Rewrite；
- 复杂任务拆解和结构化 Planning；
- 工具选择、参数生成和工具序列预测；
- Agent 状态、轨迹和错误恢复；
- Context Selection 与上下文预算；
- Verifier、Self-check 或外部校验；
- Prompt、Workflow、模型和数据方案对比；
- Agent 轨迹数据构建与 Tool-use SFT；
- 离线指标、端到端指标、消融和失败样本分析。

### 5.2 希望从本项目中看到的能力

| 岗位关注点 | 本项目应证明的能力 |
| --- | --- |
| 任务建模 | 将问题划分为事实、计算、经营质量、比较、原因、风险、澄清和拒答 |
| 结构化规划 | 复杂任务能够输出可校验的步骤、工具、参数和依赖关系 |
| 工具选择 | 能评测 Tool Accuracy、Argument Accuracy 和调用顺序 |
| 上下文选择 | 能比较不同 Context Builder 对有效证据比例和任务成功率的影响 |
| 轨迹数据 | 保存每个节点、工具、结果、错误、恢复和终止状态 |
| Verifier | 对数值、单位、口径、引用和结论范围进行独立校验 |
| 算法实验 | 有基线、单变量实验、消融、困难样本和能力退化分析 |
| 端到端验证 | 离线 Plan、Tool、Argument 提升能够转化为 Task Success 提升 |

### 5.3 最关注的项目成果

该岗位最看重以下成果：

1. 机器可读的 Query Parse 和 Plan Schema；
2. Gold Rewrite、Gold Plan、Gold Tool 与 Gold Arguments；
3. Router、固定 Workflow、ReAct 或 Plan-and-Execute 的对比；
4. Agent Trajectory Schema 和轨迹回放；
5. Tool、Argument、Plan、Clarification、Refusal 等分层指标；
6. Verifier 对错误年份、单位、口径和无证据结论的拦截结果；
7. 至少一组清晰消融，能够说明提升来自哪个模块；
8. 失败分类，如 Rewrite 错误、Planning 错误、工具错误、参数错误、检索错误和验证错误；
9. 后续基于真实轨迹构建的小规模 Tool-use SFT 数据与基线对比。

### 5.4 对应项目模块

```text
Intent Parser
Query Rewrite
Planner
Router
Context Builder
Tool Registry
Agent State
Trajectory Store
Verifier
Evaluation
Failure Taxonomy
Tool-use SFT
```

### 5.5 简历表达重点

简历应优先突出：

- 任务分解与结构化规划；
- 工具和参数正确率；
- 轨迹数据设计；
- Verifier 与错误恢复；
- 基线、消融和端到端评测；
- Tool-use SFT 是否真正改善了稳定失败。

Agent 算法方向不能只写“使用 LangGraph 编排多个节点”。需要进一步说明：

- 节点为什么这样拆；
- 路由依据是什么；
- Plan 如何表示；
- 错误如何分类；
- 哪个改动提升了什么指标；
- 是否产生过度调用、能力退化或格式正确但语义错误。

### 5.6 面试可能追问

- Agent 和确定性 Workflow 的边界是什么？
- 为什么某些任务需要 Planning，而事实查询不需要复杂规划？
- Plan 使用自由文本还是 JSON，如何评测？
- 如何定义一步 Plan 正确和整个 Plan 正确？
- Tool Accuracy 与 Argument Accuracy 为什么要分开？
- Query Rewrite 如何避免改写后语义漂移？
- Context Engineering 与 Prompt Engineering 有什么区别？
- Verifier 与主模型使用同一个模型是否会产生同源错误？
- 如何处理工具超时、空结果、部分成功和重复执行？
- 如何避免模型看到金融词就过度调用工具？
- 离线工具准确率提高但端到端 Task Success 不提高，可能是什么原因？
- SFT 数据如何避免模板泄漏和训练测试污染？
- 如何证明微调收益来自困难样本，而不是数据规模或 Prompt 差异？

### 5.7 该项目之外仍需补强

- Transformer 与注意力机制；
- 语言模型推理和生成参数；
- PyTorch 训练与调试；
- LoRA、QLoRA 和 PEFT 原理；
- 基础强化学习和偏好优化概念；
- 数据构造、采样和训练评测方法；
- ACM 模式算法题。

## 6. 目标岗位三：金融科技 / 金融 AI

### 6.1 核心职责

该岗位更关注金融业务语义、数值准确性、风险边界和企业部署条件，典型职责包括：

- 财务指标与报表口径建模；
- 财务数据抽取、清洗和质量检查；
- 结构化事实表和指标语义层；
- 单位、期间和公司口径归一化；
- 固定公式计算与同口径比较；
- 经营质量、风险披露和异常信号分析；
- 数值与证据双重校验；
- 权限、审计、人工复核和 Responsible AI；
- 私有化部署、性能、成本和数据安全；
- 与业务人员共同定义评测和交付模板。

### 6.2 希望从本项目中看到的能力

| 岗位关注点 | 本项目应证明的能力 |
| --- | --- |
| 财务口径 | 能区分营业收入、营业总收入、净利润、归母净利润等相近指标 |
| 报表范围 | 能区分合并报表与母公司报表、本期与上期、期末与期间指标 |
| 单位治理 | 保留原始值、原始单位、归一化值和展示值 |
| 数据质量 | 每个事实可追溯到报告、报表、指标行、年度列和页码 |
| 计算准确 | 关键财务计算由确定性工具完成，不由 LLM 自由口算 |
| 经营质量 | 使用多指标形成谨慎信号，而不是根据单一指标下结论 |
| 风险分析 | 区分未披露、明确为零、存在但非重大、重大事项和系统推断 |
| 可信控制 | 数值校验、证据校验、澄清、拒答和人工复核形成闭环 |
| 企业交付 | 支持日志、权限、审计、服务接口和部署说明 |

### 6.3 最关注的项目成果

该岗位最看重以下成果：

1. Company Registry 与 Report Registry；
2. Financial Metric Dictionary；
3. Financial Facts 结构化事实表；
4. Source Evidence 与双页码映射；
5. Unit Normalizer 和指标别名映射；
6. 同比、毛利率、现金利润比、资产负债率等计算工具；
7. Operating Quality Rules 和 Financial Risk Taxonomy；
8. 数值与证据双校验；
9. 高风险问题的 Human Review 记录；
10. 财务数据质量报告；
11. 经营质量或风险分析的 Executive Summary。

### 6.4 对应项目模块

```text
Company Registry
Report Registry
Financial Metric Dictionary
Financial Statement Parser
Financial Facts
Source Evidence
Financial Semantic Layer
Unit Normalizer
Financial Calculation Tools
Financial Comparison Rules
Operating Quality Rules
Financial Risk Taxonomy

```

### 6.5 简历表达重点

简历应优先突出：

- 财务语义层和数据契约；
- 数值、单位、年度和报表口径治理；
- 结构化查询与确定性计算；
- 证据追溯和双页码引用；
- 风险分类、拒答和人工复核；
- 准确性、合规性、部署成本和业务边界。

不能将“发现异常信号”写成“识别财务造假”，也不能将年报中的管理层表述写成已经独立验证的事实。

### 6.6 面试可能追问

- 营业收入和营业总收入有什么区别？
- 净利润与归母净利润为什么不能混用？
- 为什么合并报表和母公司报表必须区分？
- 资产负债表指标与利润表指标的期间类型有什么不同？
- 元、千元、万元和亿元如何避免重复换算？
- 百分比差异与百分点差异如何区分？
- 为什么现金利润比不能单独代表经营质量？
- “无重大诉讼”为什么不等于“没有任何诉讼”？
- 对外担保、对子公司担保和担保总额如何区分？
- 结构化数据与原文冲突时系统如何处理？
- 哪些结论必须人工复核？
- 如何防止系统输出投资建议或未经证实的造假判断？
- 私有化部署时需要考虑哪些数据安全与审计问题？

### 6.7 该项目之外仍需补强

- 三大财务报表及其基本勾稽关系；
- 常见财务比率和经营质量指标；
- 会计口径、审计证据和风险控制基础；
- 金融数据安全和合规意识；
- 企业私有化部署的基础概念；
- 不能把本项目包装成专业审计、法律意见或投资决策系统。

## 7. 目标岗位四：企业 AI / 咨询数字化

### 7.1 核心职责

该岗位更关注如何从企业业务流程中识别适合 AI 的环节，并把技术系统转化为可交付、可治理和可解释的解决方案，典型职责包括：

- 访谈和梳理业务需求；
- 将模糊问题转化为任务、数据和验收标准；
- 设计 AI 与人工协作流程；
- 定义风险等级、控制点和升级机制；

## 9. 项目后续必须完成的核心能力

以下能力属于 `MUST`。缺少其中多项时，项目不应被表述为已经完成的简历主项目。

### 9.1 数据与语义层

- 12 份年报完成统一登记和版本管理；
- 文档、页面、章节和 Chunk 具有稳定元数据；
- 建立公司、报告和财务指标字典；
- 建立一组核心 Financial Facts；
- 保留原始数值、原始单位、标准单位和来源页码；
- 能识别合并报表与母公司报表；
- 能处理常见指标别名和单位换算；
- 输出数据质量报告和人工抽查记录。

### 9.2 RAG 与证据层

- 完成基础向量 RAG；
- 建立固定检索开发集；
- 至少比较 Chunk 策略；
- 支持公司、年度和章节过滤；
- 返回报告、章节、印刷页码和 PDF 页码；
- 无充分证据时拒绝生成确定性结论；
- 能区分检索错误、排序错误和生成错误。

### 9.3 Agent 与工具层

- 能识别回答、澄清和拒答；
- 事实查询优先使用结构化工具；
- 精确计算由固定公式工具完成；
- 原因和风险任务使用文档证据；
- 复杂问题能够生成结构化计划；
- 工具参数经过 Schema 校验；
- 有最大步数、超时、重试、失败终止和降级；
- 轨迹可以回放。

### 9.4 可信控制层

- 每个核心结论绑定证据；
- 数值、年度、单位和口径经过校验；
- 区分公司披露、系统计算和系统推断；
- 参数缺失时一次性澄清关键字段；
- 证据不足、数据冲突或越界请求能够正确处理；
- 高风险结论进入人工复核；
- 投资预测、具体买卖建议和无证据造假判断被拒绝。

### 9.5 评测与实验层

- 74 道问题框架可机器读取；
- 至少完成 MVP 所需问题的真实标注和冻结测试；
- 保留基础 RAG、改进 RAG 和 Agent 基线；
- 评测检索、工具、参数、数值、引用、回答、澄清和拒答；
- 所有改进使用相同测试集；
- 保存逐题结果和失败分类；
- 简历中出现的每个数字都有实验表、日志或脚本来源。

### 9.6 工程交付层

- FastAPI 提供核心服务接口；
- Pydantic 完成请求和响应校验；
- 保存请求、状态、错误和 Trace；
- 编写单元测试和 API 集成测试；
- Docker 能启动核心流程；
- README 包含架构、数据、启动、示例、评测和限制；
- 至少完成一次可复现技术演示。

## 16. Week 1 阶段结论

本项目的求职价值不在于堆叠 Agent、RAG、金融和部署术语，而在于形成一组可以相互验证的工程证据：

- 用真实企业文档定义业务问题；
- 用结构化数据和固定公式保证精确数值；
- 用 RAG 和页码引用支持原因与风险结论；
- 用 Agent 工作流组织工具、检索、澄清和拒答；
- 用 Verifier、人工复核和 Responsible AI 控制高风险输出；
- 用固定评测集、基线、消融和失败案例证明系统效果；
- 用 FastAPI、测试、Docker 和 README 完成交付；
- 用真实实验结果支持简历和面试表达。

因此，后续开发的最高优先级不是增加更多功能，而是持续完善：

```text
可运行
+ 可评测
+ 可追溯
+ 可复现
+ 可解释
+ 可交付
```

`04_job_track_requirements.md` 将作为后续架构设计、任务优先级、实验设计、项目验收以及最终多岗位简历表达的共同依据。
