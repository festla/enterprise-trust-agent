# Week 01：平台层与金融领域适配边界

## 1. 文档目标

本文档用于明确企业可信文档分析 Agent 的系统边界，区分：

1. 可在不同企业文档场景中复用的通用平台能力；
2. 面向上市公司年报与财务分析的金融领域能力；
3. 当前 MVP 阶段明确不实现的功能；
4. 各模块之间的依赖方向与调用原则。

本项目不是单纯的“上传 PDF 后让大模型总结”，而是一个围绕企业文档构建的可信分析 Agent。系统需要能够基于文档和结构化数据完成事实查询、指标计算、跨期与同业比较、经营质量分析、原因归因、风险识别、证据引用、结果校验以及拒答和澄清。

---

## 2. 系统定位

### 2.1 项目目标

系统面向上市公司年报及相关企业文档，提供以下能力：

- 查询指定公司、年度和口径的财务事实；
- 使用结构化数据和固定公式完成财务计算；
- 对多个指标进行组合分析；
- 完成跨年度与跨公司的同口径比较；
- 根据管理层讨论、财务附注和风险章节解释经营变化；
- 对回答中的数值、证据和结论进行校验；
- 在证据不足、条件不完整或超出能力边界时拒答或澄清；
- 对高风险结论保留人工复核入口。

### 2.2 可信性的含义

本项目中的“可信”主要包括：

- 数值可追溯：能够定位到原始报表、指标行、年度列和单位；
- 证据可追溯：能够定位到报告、章节、印刷页码和 PDF 页码；
- 计算可复核：公式、输入值、单位归一化和结果均可检查；
- 口径可解释：区分合并报表与母公司报表，区分营业收入、营业总收入、净利润和归母净利润；
- 推断有边界：区分公司直接披露、系统计算结果与系统分析推断；
- 高风险可升级：涉及诉讼、担保、财务异常、造假判断等事项时，可进入人工复核；
- 越界可拒绝：不预测股价，不提供具体买卖建议，不在证据不足时给出确定性结论。

---

## 3. 总体分层

系统初步划分为五层：

```text
交互与 API 层
        ↓
Agent 与工作流层
        ↓
通用平台能力层
        ↓
金融领域适配层
        ↓
文档、结构化数据与外部数据源
```

评测与可观测性作为横向能力，覆盖所有层级。

---

## 4. 通用平台能力层

通用平台层提供与具体行业无关的基础能力。未来将年报替换为合同、审计报告、政策文件或内部制度文档时，这些模块仍然可以复用。

### 4.1 Document Loader

职责：

- 接收 PDF、Word、Markdown、HTML 等文档；
- 提取文本、页码、标题、表格和基础元数据；
- 记录文档来源、文件名、版本和载入时间；
- 处理读取失败、空文档和格式异常。

不负责：

- 判断“营业收入”或“归母净利润”的业务含义；
- 计算财务指标；
- 判断某项诉讼是否重大。

### 4.2 Metadata Manager

职责：

- 统一管理文档级、页级、章节级和片段级元数据；
- 保存文档 ID、来源、公司、年度、文档类型、页码、章节路径；
- 为后续检索、引用和校验提供统一元数据接口。

基础元数据至少包括：

```text
document_id
document_type
source_name
file_name
version
page_number
printed_page
section_title
subsection_title
chunk_id
created_at
```

### 4.3 Chunking

职责：

- 按章节、段落、表格和语义边界切分文档；
- 避免表格标题、单位和数据行被错误拆分；
- 保留片段与原始页面之间的映射关系；
- 为不同文档类型提供可配置切分策略。

### 4.4 Retriever

职责：

- 根据问题检索相关文档片段；
- 支持关键词检索、向量检索和混合检索；
- 支持公司、年度、文档类型和章节过滤；
- 返回可追溯的候选证据。

不负责：

- 直接生成最终答案；
- 判断财务指标口径；
- 执行精确计算。

### 4.5 Reranker

职责：

- 对检索结果进行二次排序；
- 提升与问题、公司、年度和章节的匹配度；
- 降低相似但口径错误的片段排名；
- 为证据组合提供更高质量候选结果。

### 4.6 Planner

职责：

- 判断问题属于事实查询、计算、比较、原因分析、风险分析、澄清或拒答；
- 将复杂问题拆分为可执行步骤；
- 决定调用哪些工具以及调用顺序；
- 检查必要参数是否完整；
- 在参数缺失时发起澄清。

Planner 不应直接完成精确数值计算，也不应绕过工具伪造结果。

### 4.7 Tool Registry

职责：

- 注册系统可调用工具；
- 维护工具名称、说明、输入参数和输出结构；
- 校验工具参数；
- 控制工具访问权限和调用范围；
- 记录工具执行日志。

### 4.8 Context Manager

职责：

- 管理当前会话状态；
- 保存用户已确认的公司、年度、指标口径；
- 避免重复询问已经明确的信息；
- 控制输入给模型的上下文长度；
- 防止不同公司、不同年度的信息相互污染。

### 4.9 Evidence Manager

职责：

- 为答案中的每个关键结论绑定证据；
- 区分数值证据、管理层表述、风险披露和系统推断；
- 记录证据 ID、页码、章节和来源；
- 检查关键结论是否存在直接支持。

### 4.10 Citation Builder

职责：

- 根据证据元数据生成统一引用；
- 同时保留印刷页码和 PDF 页码；
- 保证引用与答案中的具体结论相匹配；
- 避免只给出文档名而缺少页码和章节。

### 4.11 Verifier

职责：

- 检查公司、年度、指标和报表口径是否正确；
- 检查工具调用结果与答案是否一致；
- 检查单位换算和计算公式；
- 检查引用是否能够支持答案；
- 检查分析结论是否超出证据；
- 对高风险答案给出通过、警告或人工复核状态。

### 4.12 Human Review

职责：

- 接收高风险或存在冲突的结果；
- 展示问题、答案、证据、计算过程和模型推断；
- 允许人工确认、修改或驳回；
- 记录审核意见与最终状态。

### 4.13 Evaluation

职责：

- 执行事实准确率、工具准确率、参数准确率、引用准确率等评测；
- 检查数值是否在容差范围内；
- 检查应答、澄清和拒答动作是否正确；
- 支持 dev、validation 和 test 数据集；
- 输出失败案例和错误分类。

### 4.14 Observability

职责：

- 记录每次请求的规划路径；
- 记录工具调用、参数、耗时和错误；
- 记录检索片段和最终引用；
- 记录 Token、成本和整体延迟；
- 支持问题复现和性能分析。

### 4.15 API 与服务层

职责：

- 提供统一请求入口；
- 负责参数校验、身份校验和错误返回；
- 支持同步和流式响应；
- 对外暴露 Agent 能力，但不暴露底层内部实现细节。

## 5. 金融领域适配层

金融领域适配层负责把通用平台能力应用到上市公司年报和财务分析场景。

### 5.1 Company Registry

职责：

- 维护公司标准名称、简称、股票代码和内部公司 ID；
- 处理同一公司的不同名称写法；
- 为跨公司检索和比较提供唯一标识。

示例：

```text
midea
gree
haier_smart_home
hisense_home
robam
supor
```

### 5.2 Report Registry

职责：

- 维护公司、年度与年报文件之间的映射；
- 记录报告类型、披露日期、版本和文档质量；
- 区分年度报告、半年度报告和季度报告；
- 防止错误使用非目标年度或非目标报告。

### 5.3 Financial Metric Dictionary

职责：

- 定义统一的财务指标 ID；
- 维护中文名称、别名、来源报表和单位；
- 区分相近但不同的财务指标；
- 为查询工具和计算工具提供标准口径。

示例：

```text
revenue
total_operating_revenue
operating_profit
net_profit
net_profit_attributable_to_parent
net_cash_flow_from_operating_activities
inventory
accounts_receivable
total_assets
total_liabilities
research_and_development_expense
```

### 5.4 Financial Statement Parser

职责：

- 识别资产负债表、利润表和现金流量表；
- 识别指标行、年度列和表格单位；
- 提取合并报表与母公司报表数据；
- 记录比较数据是否发生重列；
- 将原始值映射为统一结构。

### 5.5 Financial Semantic Layer

职责：

- 解释指标之间的业务关系；
- 区分营业收入和营业总收入；
- 区分净利润和归母净利润；
- 区分经营活动现金流净额与现金及现金等价物净增加额；
- 区分对外担保、对子公司担保和公司担保总额；
- 区分“无重大诉讼”与“无任何诉讼”。

### 5.6 Unit Normalizer

职责：

- 识别元、千元、万元、百万元和亿元；
- 将结构化数值统一归一化为标准单位；
- 保留原始单位与原始数值；
- 支持答案展示时按需换算；
- 防止跨公司比较时单位混乱。

建议内部标准单位：

```text
货币金额：CNY
百分比：percent
比例：ratio
每股指标：CNY_per_share
```

### 5.7 Financial Calculation Tools

职责：

- 使用固定公式完成精确计算；
- 禁止由大模型直接口算关键财务指标；
- 输出公式、输入值、单位和结果；
- 支持容差评测。

MVP 计算工具包括：

```text
calculate_growth_rate
calculate_financial_ratio
compare_financial_metrics
```

常见公式包括：

```text
同比增长率
销售毛利率
现金利润比
资产负债率
流动比率
研发费用率
归母净利润率
经营现金流占营业收入比例
```

### 5.8 Financial Comparison Rules

职责：

- 保证比较公司使用同一年度；
- 保证指标定义和报表口径一致；
- 保证单位已归一化；
- 区分百分比差异和百分点差异；
- 提醒用户绝对规模不能直接代表经营效率。

### 5.9 Operating Quality Rules

职责：

- 使用多个指标形成经营质量信号；
- 对利润增长、现金流、应收账款、存货和负债进行组合判断；
- 输出谨慎结论和限制条件；
- 避免根据单一指标直接判断公司经营优劣。

MVP 信号示例：

```text
cash_conversion_strengthened
cash_conversion_weakened
inventory_growth_relatively_controlled
inventory_pressure_increased
receivable_growth_faster_than_revenue
short_term_solvency_improved
short_term_solvency_weakened
```

### 5.10 Financial Risk Taxonomy

职责：

- 定义风险类型和机器可读标签；
- 区分风险是否披露、事项是否存在和事项是否重大；
- 统一诉讼、仲裁、担保、减值、关联交易和或有事项的表示方式。

风险字段建议区分：

```text
section_disclosed
disclosure_status
item_exists
materiality
amount
evidence_ids
human_review_required
```

### 5.11 Financial Evidence Templates

职责：

- 为不同任务定义证据模板；
- 事实题要求报表、指标行、年度列和单位；
- 原因题要求管理层表述和结构化数据共同支撑；
- 风险题要求同时检索重要事项章节和财务报表附注；
- 区分直接披露与系统推断。

## 6. 通用层与金融层的边界

| 能力 | 通用平台层 | 金融领域适配层 |

| 文档读取 | 负责 | 不负责 |
| 文档切分 | 负责 | 提供财报专用规则 |
| 元数据管理 | 负责通用结构 | 增加公司、年度、报表等字段 |
| 检索 | 负责检索机制 | 提供财务章节与关键词 |
| 规划 | 负责流程规划 | 提供财务任务类型与工具 |
| 工具调用 | 负责注册和执行 | 提供财务查询与计算工具 |
| 指标定义 | 不负责 | 负责 |
| 单位归一化 | 提供通用接口 | 实现财务单位规则 |
| 财务公式 | 不负责 | 负责 |
| 经营质量规则 | 不负责 | 负责 |
| 风险分类 | 提供通用风险接口 | 实现财务风险分类 |
| 证据管理 | 负责通用证据结构 | 提供财务证据模板 |
| 引用生成 | 负责 | 提供页码和章节元数据 |
| 答案校验 | 负责校验流程 | 提供金融口径校验规则 |
| 人工复核 | 负责流程 | 提供高风险触发条件 |
| 评测 | 负责框架 | 提供财务评测集和标签 |

## 7. 依赖原则

### 7.1 单向依赖

模块依赖应保持以下方向：

```text
交互/API
  ↓
Agent/Workflow
  ↓
通用平台接口
  ↓
金融领域实现
  ↓
文档与结构化数据
```

不允许出现：

- 通用平台层直接硬编码公司名；
- 通用检索器直接硬编码营业收入等指标；
- API 层直接读取数据库并拼接财务答案；
- LLM 绕过工具直接计算关键指标；
- 金融工具反向依赖具体前端或 API；
- 评测代码与业务代码强耦合。

### 7.2 工具优先

对于可结构化查询和精确计算的任务，应优先使用工具。

例如：

```text
查询营业收入 → query_financial_metric
计算同比增长率 → calculate_growth_rate
计算毛利率 → calculate_financial_ratio
跨公司比较 → compare_financial_metrics
检索原因与风险 → search_document_evidence
```

### 7.3 证据优先

最终答案中的核心事实必须有直接证据支持。

- 数值结论需要报表证据；
- 原因结论需要管理层讨论或附注证据；
- 风险结论需要重要事项章节和财务附注证据；
- 系统推断必须明确标记为推断，不能伪装成公司直接披露。

### 7.4 高风险复核

以下情况默认需要人工复核：

- 诉讼、仲裁和担保事项；
- 财务造假、欺诈或违规判断；
- 重大异常或重大风险结论；
- 数据源之间存在冲突；
- 证据无法完整支持结论；
- 模型需要对管理层表述进行较强推断。

## 8. 当前 MVP 范围

当前 MVP 仅覆盖：

- 6 家家电行业上市公司；
- 每家公司 2024 年和 2025 年年度报告；
- 共 12 份文本型 PDF；
- 74 道评测问题；
- 事实查询、数值计算、经营质量、同业比较、原因、风险、拒答和澄清；
- 合并财务报表为主要结构化数据口径；
- 年报印刷页码和 PDF 页码双重引用；
- 基础 Agent 工作流、工具调用、证据校验和人工复核标记。

---

## 9. 当前 MVP 明确不做的内容

为避免项目范围失控，当前阶段明确不实现：

1. 不覆盖所有上市公司；
2. 不接入实时股票行情；
3. 不预测股价或投资收益；
4. 不提供具体买入、卖出或持有建议；
5. 不自动认定公司存在财务造假；
6. 不输出法律、审计或投资方面的最终专业结论；
7. 不处理大量扫描质量极差或无法提取文字的 PDF；
8. 不训练自有大语言模型；
9. 不微调领域大模型；
10. 不建设完整企业级知识图谱；
11. 不实现全自动财务审计；
12. 不接入全部公告、新闻、研报和舆情数据；
13. 不实现复杂多租户权限系统；
14. 不在 Week 1 开始生产级部署和性能优化；
15. 不把所有企业文档场景一次性纳入系统。

## 10. 边界场景处理规则

### 10.1 参数缺失

当公司、年度、指标口径无法唯一确定时：

```text
expected_action = clarify
```

系统应一次性询问所有关键缺失字段，不应擅自默认最新年度或归母净利润。

### 10.2 证据不足

当年报中不存在足够证据时：

- 说明未找到足够证据；
- 返回已经检索的章节范围；
- 不编造原因或风险；
- 必要时要求人工复核。

### 10.3 数据冲突

当结构化数据与文档证据冲突时：

- 暂停生成确定性答案；
- 标记冲突字段；
- 展示两种来源及差异；
- 将结果升级为人工复核；
- 评测状态可标记为 `disputed`。

### 10.4 投资决策请求

对于股价预测、收益预测和具体买卖建议：

```text
expected_action = refuse
```

拒绝后可以提供：

- 历史财务分析；
- 年报风险摘要；
- 管理层展望；
- 不包含交易指令的情景分析。

### 10.5 财务欺诈判断

系统可以：

- 识别异常信号；
- 总结风险证据；
- 提供需要进一步核验的事项。

系统不可以：

- 在证据不足时认定财务造假；
- 将异常指标直接等同于欺诈；
- 输出未经审计或调查确认的确定性指控。

---

## 11. 设计原则总结

本项目后续开发应持续遵守以下原则：

1. 通用平台与金融领域能力解耦；
2. 结构化查询优先于生成式回答；
3. 精确计算必须由工具完成；
4. 每个核心结论都应有证据；
5. 公司披露、系统计算和系统推断必须区分；
6. 重要数值保留原始值、归一化值和展示值；
7. 页码同时保留印刷页码和 PDF 页码；
8. 高风险任务允许人工复核；
9. 参数不完整时先澄清；
10. 超出能力边界时明确拒答；
11. MVP 先完成可信闭环，再扩展功能；
12. 架构设计应支持未来替换行业适配层，而不重写通用平台。

## 12. Week 1 阶段结论

通过本次边界设计，项目已经明确：

- 什么属于通用 Agent 平台；
- 什么属于金融领域专用能力；
- Agent 应如何调用工具、检索证据并验证结果；
- 哪些问题需要回答、澄清、拒答或人工复核；
- 当前 MVP 做到什么程度；
- 哪些功能明确留到后续阶段。

该边界将作为后续初始架构设计、数据契约设计、工具实现和评测开发的共同依据。
