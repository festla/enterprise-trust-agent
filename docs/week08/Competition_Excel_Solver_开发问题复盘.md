# Competition Excel Solver 开发问题复盘

## 1. Excel 文件格式与表格结构复杂

### 问题
比赛附件中同时存在 `.xlsx` 和 `.xls` 文件，并且真实表格中存在合并单元格、公式单元格、超大声明行列范围、多层表头等情况。直接按完整二维矩阵读取容易浪费内存，也会影响后续定位。

### 解决方法
- `.xlsx` 使用 `openpyxl`，`.xls` 使用 `xlrd`。
- 使用稀疏 Cell 结构保存实际存在的单元格，而不是遍历 `max_row × max_column`。
- 统一保留坐标、行列索引、数值、文本、公式、缓存值、Number Format 和合并区域。

### 结果
389 个 Excel 文件均可解析，后续三个 Solver 共用同一套结构化 Excel 表示。

## 2. 表格取数时原始浮点值与答案显示精度不一致

### 问题
Excel 中的真实值可能为：

`259039.987564867`

而题目选项显示为：

`259039.99`

如果直接比较浮点数，或者使用过于宽松的相对误差，都可能造成误判。

### 解决方法
使用 `Decimal`，根据每个选项自身的小数位数进行 `ROUND_HALF_UP` 后再匹配答案，并在多个选项同时匹配时拒绝猜测。

### 结果
表格取数 Frozen Dev 达到 **12/12**。

---

## 3. 题目中的指标名称与 Excel 行标签并不完全一致

### 问题
题目选项可能是：

- `寿险`
- `大型商业银行`
- `机动车辆保险`

但 Excel 中实际写成：

- `其中：寿险`
- `其中：大型商业银行`
- `其中：机动车辆保险`

单纯使用文本完全相等会导致定位失败。

### 解决方法
设计保守的 Option Label Resolver：

1. 标准化后的精确匹配；
2. 去除“其中”等结构性前缀后匹配；
3. 必要时使用受限制的短文本包含匹配；
4. 避免匹配到长备注或说明文字。

### 结果
解决了多道比较题中的标签变体问题。

---

## 4. 同一个指标可能在一张表中重复出现

### 问题
部分 Excel 中包含多个数据区块，同名指标会重复出现。例如“资金运用余额”“年化财务收益率”等可能分别出现在总体、人身险公司、财产险公司区块中。

如果只根据标签找数字，会得到多个同分候选，无法知道应该使用哪一个。

### 解决方法
加入 **Comparable Section Resolution**：

- 收集 A/B/C/D 对应的所有 Label 候选；
- 根据空间距离寻找紧凑、连续的可比较区块；
- 优先选择包含更多选项、结构更完整、位置更合理的区块；
- 只在选中的 Section 内进行数值定位与比较。

### 结果
表格比较从最初 **5/11**，经过标签和 Section 解析改进后提升到 **11/11**。

## 5. “数值最高”不一定意味着四个选项的原始数字都应直接比较

### 问题
部分题目中，一个选项虽然在 Excel 中数值非常大，但它属于另一个业务指标区块，并不属于题目真正要求比较的集合。

例如“新增保险金额”与“原保险保费收入、寿险、意外险”虽然都出现在同一张表中，但并不属于同一个可比较 Section。

### 解决方法
先判断语义上和空间上属于同一区块的候选项，再执行 `max/min`，而不是把四个选项找到的任意数字直接比较。

### 结果
避免了“数学上最大，但业务口径上不可比较”的错误。

---

## 6. 计算题中部分目标列没有明确可见表头

### 问题
计算题统一是：

`变化值 = 终点值 - 起点值`

大部分题目可以通过“实体行 + 起点表头 + 终点表头”定位两个 Cell。

但个别题目中，Gold 使用的目标 Cell 并没有对应的可见表头。如果强行建立固定映射，会变成硬编码。

### 解决方法
采用两级解析：

1. **semantic_headers**  
   能从真实表头确定起点和终点时，直接定位 Cell。

2. **option_constrained_fallback**  
   如果某个表头无法从 Excel 中真实确定，只在同一实体行中枚举候选 Cell，执行确定性计算，并且只有在结果能唯一匹配一个选项时才返回。

同时在结果中记录 `resolution_mode`，避免伪造“这是通过表头找到的”。

### 结果
计算题 Frozen Dev 达到 **10/10**，其中：

- `semantic_headers`：9
- `option_constrained_fallback`：1

## 7. 避免评测数据泄漏

### 问题
比赛 QA 文件中同时包含问题、答案和 Evidence。如果 Solver 直接使用完整 Case，很容易无意中把 Gold 信息带入推理过程。

### 解决方法
将数据拆分为：

- `CompetitionQuestion / SolverInput`：仅供 Solver 使用；
- `CompetitionGold`：仅在预测完成后用于评测。

同时冻结 Dev/Test Source Split，开发过程中只基于 Dev 做 Failure Analysis。

### 结果
当前 Excel Solver 的成绩可以明确表述为：

| 类型 | Frozen Dev |
|---|---:|
| 表格取数 | 12/12 |
| 表格比较 | 11/11 |
| 表格计算 | 10/10 |
| **总计** | **33/33** |

> 该结果仅代表 Frozen Dev，不代表尚未评测的 Test 集准确率。

---

## 阶段性结论

这一阶段最重要的经验是：**Excel QA 的难点并不在算术本身，而在于可靠地确定“哪个 Cell 才是题目真正要求的证据”。**

因此最终没有让 LLM 直接处理 Excel 数值，而是将流程拆成：

`Excel Parser → Label/Header Resolver → Comparable Section / Operand Resolver → Deterministic Calculation → Option Resolver → Evidence`

整个开发过程主要采用 **Failure-driven Development**：先运行真实 Dev，定位失败类型，再增加通用解析能力，而不是针对具体 Case ID 编写规则。
